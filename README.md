## 第1章 AI活用は、5段階で進化してきた

AI活用の進化は、「人間が細かく指示する時代」から「AI同士が組織的に動く時代」へ進んでいる。

| 段階 | 名称 | 内容 |
|---|---|---|
| Stage1 | プロンプトエンジニアリング | 人間がAIに細かく指示する時代 |
| Stage2 | エージェントエンジニアリング | AIに手足が生え、外部ツールを使える時代 |
| Stage3 | ワークフロー／AI社員 | 司令塔AIが複数のAIに役割分担させる時代 |
| Stage4 | ループエンジニアリング | AI同士が検証・修正・再実行を繰り返す時代 |
| Stage5 | グラフエンジニアリング | AIたちが組織のように相互接続する時代 |

一言でいうと、AI活用は「プロンプトを書く技術」から「AIが働く環境を作る技術」へ進み、さらに「AI同士が組織として機能する構造を設計する技術」へ進化している。これが、グラフエンジニアリングに行き着く道筋だ。

## 第2章 Stage1〜3：指示する時代からAI社員の時代へ

最初は、ChatGPTのような対話型AIに対して、人間が細かく指示を出す時代だった（**Stage1 プロンプトエンジニアリング**）。「何文字で書いて」「この形式で出して」「あなたは〇〇の専門家として答えて」——人間がどれだけ丁寧に条件や役割を与えられるかが成果を左右していた。AIは賢いけれど、基本的には"会話相手"であり、人間が都度指示する必要があった。

次に、AIが外部ツールを使えるようになり、**Stage2 エージェントエンジニアリング**の時代に入った。Gmailを見に行く、Google Driveを探す、Slackに通知する、画面を操作するなど、AIに"手足"が生えたイメージだ。ここで重要になったのが、AIが動ける環境を整えること。スキル、MCP、外部サービス連携、操作権限、マニュアルなどを与えることで、AIがより自由に動けるようになる。プロンプトそのものより、AIが走り回れる環境設計が大事になった。

その次に出てきたのが、**Stage3 AI社員・サブエージェント・ワークフロー**の考え方だ。1つのAIに全部やらせるのではなく、司令塔AIが複数のAIを使い分ける。実行役、調査役、文章作成役、検証役のように役割分担させることで、より効率よく仕事を進められるようになった。

## 第3章 Stage4：そもそも「ループ」って何？

Stage3にも問題があった。結局、人間が途中で何度も確認し、修正指示を出さなければならない。AI社員に任せているようで、実際には人間がずっと管理し続ける必要があった。

そこで出てきたのが**Stage4 ループエンジニアリング**——AI同士に検証・修正・再実行をさせる考え方だ。人間が毎回細かく直すのではなく、最初にゴールや評価基準を与える。あとはAIたちが互いに成果物をチェックし、修正し、改善を繰り返す。人間は細かい指示者ではなく、**ゴール設定者**になる。

たとえるなら、**1人で切り盛りする屋台**を思い浮かべてほしい。仕入れも接客も会計も、全部自分でこなす——これが「ループ」の正体だ。

- **トリガー**: お客さんが来たら動き出す
- **タスク**: 注文を聞き、作り、会計する
- **成功基準**: 満足して帰ってもらう

この3つを1人でぐるぐる回す仕組みが「ループ」。今、多くの業務がこの形で自動化されている。

## 第4章 ループの限界

しかし、ループにも限界がある。実行役・修正役・検証役がいても、**「その検証役自体は、誰が検証するのか？」**という問題が残る。また、AIが出した最終結果に対する責任は、結局人間や組織が負う必要がある。

屋台にお客さんが増えると、何が起きるか。**1人にすべての仕事が集中し、対応しきれなくなる**。この状態を分解すると、ループが抱える3つの問題が見えてくる。

| 問題 | 内容 |
|---|---|
| ① コンテキストの劣化 | 抱える情報が増えるほど、AIの回答の質が落ちていく |
| ② 自己採点の甘さ | 自分が作ったものを自分で評価するので、見落としが起きやすい |
| ③ 遅い・詰まりが見えない | 1つずつ順番にこなすので時間がかかり、どこで問題が起きたか分かりにくい |

これが、1人担当の「ループ」がぶつかる壁だ。

## 第5章 Stage5：グラフで何が良くなるか

最後に出てくるのが**グラフエンジニアリング**。AIを単なる直線的なワークフローではなく、**組織のようなネットワーク構造**で動かす考え方だ。実行役、検証役、修正役、調査役などが一方向に並ぶのではなく、相互につながり、互いにチェックし合う。

会社組織でいうと、人事・SNS・営業・管理部門がそれぞれ独立しているだけでなく、互いに連携し、牽制し、品質を高め合っている状態に近い。つまりグラフエンジニアリングとは、**AI同士を役割ごとに配置し、それぞれが相互に検証・修正・連携する構造を設計すること**だ。

屋台の店主が、仕入れ担当・接客担当のスタッフを雇うとどうなるか。それぞれが自分の持ち場だけに集中し、店長は全体をつなぎ、最終チェックする。これが「グラフ」の入り口——ループを役割ごとに分けてつなぐ構成だ。

### 実例：毎朝のレポート作成

| | 内容 |
|---|---|
| **ループ版（Before）** | 1エージェントがYouTube・X・Reddit・メールを順番に自分で巡回し、集めた情報を自分で統合してレポートを作成。担当が1つに集中し、コンテキストが膨らみやすい |
| **グラフ版（After）** | YouTube担当・X担当・Reddit担当・メール担当の4エージェントに分割。各担当が自分の持ち場だけをループで処理し、レポート担当が全員の結果を統合。質が上がり、速くなり、詰まった箇所も一目で分かる |

核心はシンプルだ。**グラフは、タスクを「それぞれ自分のループを回す担当」に分けただけ**——各スタッフも、結局は自分の持ち場のループを回している。

## 第6章 公式データが示す効果

これは単なる流行り言葉ではない。Anthropic公式が2025年6月に公開した研究では、Opus主導のリードエージェントが複数のサブエージェントを統括する構成が、単一エージェント比で**90.2%**の性能向上を示した ✅（[出典を見る →](https://www.anthropic.com/engineering/multi-agent-research-system) Anthropic Engineering「How we built our multi-agent research system」）。

そのほかにも、担当を分けた設計で効果が確認された報告がある。不動産会社の物件チェックAIの例では、「本当は問題ない物件」を誤って「問題あり」と止めてしまう割合（誤検出率）が、担当を分け、受け渡し方（配線）まで設計するほど下がっていった。

| 構成 | 誤検出率 | 目安 |
|---|---|---|
| 店主1人で判定（単一プロンプト） | 35% | 約3件に1件 |
| スタッフで分担（エージェントチーム） | 8% | 約13件に1件 |
| 配線まで設計（明示的グラフ） | **2%** | 約50件に1件 ⚠️ |

また、自由実行のループを構造化された計画に置き換えると、ツール呼び出しの実行精度が41%→**96%**に改善したという報告もある 🔶。

## 第7章 グラフを使った方がいい理由

ここまでの内容から、結論は明快だ。**担当を分けて相互に連携させる「グラフ」に変えるだけで、質・速度・分かりやすさが改善する。**

ただし、グラフはすべての業務に必要なわけではない。特にこういう時に効果を発揮する 🔶（英語解説動画での整理）。

1. **情報量が多いとき**——抱える情報が増え、質が落ちてきたと感じたら
2. **第三者の目が要るとき**——自分で作ったものを自分で採点するのが不自然な場面
3. **とにかく急ぐとき**——複数の作業を同時に、素早く終わらせたい場面

この3つに当てはまる業務から、担当分けを試してみてほしい。

## 今日からやること

始めるならこの順番。

1. **今動かしている業務ループを1つ思い浮かべる**——SEO記事作成、カスタマー対応、経理処理、なんでもよい
2. **3条件に当てはまるか確認する**——情報量／第三者チェック／速度。1つでも当てはまれば検討の価値あり
3. **プレゼントのテンプレを1つ、そのままコピーして試す**——業務別のBefore/After型なので、置き換えるだけで使える
4. **効果を感じたら、担当をさらに分けて本格運用へ**
